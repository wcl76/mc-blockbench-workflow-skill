# 模型清单、联动与命名

主题确定后规划模型、处理后续新增资产、创建目录或分组时读取。清单持续维护，不要求一次列完，也不将候选项自动当作制作任务。

## 渐进式模型清单

主题确定后问：“这个主题下，你已经想做哪些模型？可以先选几个，也可以只做当前这一件，之后再补充。”

根据主题提供少量具体候选，例如高斯科技可选卡宾枪、精确射手步枪、能源匣或配件；乡村家具可选桌椅、柜子或灯具。同时提供“只做当前模型”和“暂不列清单，后续再补充”的路径。用户明确不需要选项时直接接收自由描述，不强行推荐整套资产。没有选择的候选只记为建议，不建模。

建立以下持续更新的模型清单：

| 模型 ID | 中文展示名 | 分类／系列 | 主题对应 | 状态 | 关联模型／接口 | 本次范围 |
| --- | --- | --- | --- | --- | --- | --- |
| 稳定 ID | 用户易懂名称 | 如 weapons／gauss | 沿用哪些设计元素 | 建议／计划／制作中／完成／搁置 | 无、待定或关系 ID | 本次做／以后做／未决定 |

用户后续提出新模型时，核对主题、风格和已有接口，补入清单并直接进入该资产需要的工作。若与现有主题明显冲突，指出具体差异，提供融入主题的版本或询问是否调整主题，不静默改写整个项目方向。

## 模型间联动

只询问与当前资产有关的关系：“哪些模型需要共用、连接、更换部件或一起运动？现在不确定也可以先留接口。”

| 关系 | 应记录的内容 |
| --- | --- |
| 可替换配件 | 主体、槽位、兼容配件、接口坐标／朝向／单位、挂接节点、互斥规则 |
| 连接／拼装 | 接口尺寸与间隙、方向、连接对象，例如管道与机器 |
| 组合／同步运动 | 谁驱动谁、局部轴心、关联动作或事件，例如设备与活动模块 |
| 共享部件／材质 | 唯一来源、引用资产、UV 与纹理契约、允许差异 |
| 同系列外观 | 共用比例、标志、材质和配色；不把外观相似误写成可互换 |

记录来源与目标的模型 ID、关系 ID、接口 ID、当前已确认或待定内容及验证状态。未知兼容性记为待定，不承诺任意配件通用。新配件先在接口处检查尺寸、方向、穿插与必要运动姿态；编辑器组合检查不能代替游戏侧切换逻辑验证。当前只制作主体时保留适当接口即可，不提前制作全部候选配件。

同一共享配件保留一个源资产，以引用关联多个主体；独有部件留在主体内。若目标格式要求导出时合并，可生成组合资源，但仍保存独立源文件及关系记录，后续更换单件不用重做整套模型。

## 目录与文件命名

新项目使用下面约定；已有项目沿用其规范，记录对应关系，不为套用本约定批量改名或移动既有资源。目录是磁盘组织，Blockbench 分组／骨骼是运动结构，两者不能混用。

- 项目、分类、系列、模型的 ID 使用小写英文或有含义的拼音，单词用连字符，如 `gauss-tech`、`gauss-carbine`；仅含 `a-z`、数字和单个连字符，以字母开头，避免空格、Windows 保留名及“new/final/最终版”等临时含义。
- 中文展示名保存在清单中。模型 ID 在项目内唯一，选定后保持稳定；变更 ID 时同步文件引用、关联清单和资源接入。
- 固定目录名：`project`（项目汇总）、`concepts`（概念图）、`models`（模型源资产）。模型分类按当前项目选择，如 `weapons`、`furniture`、`machines`、`creatures`、`attachments`；分类与系列目录只按实际资产建立。
- 概念图名：`<asset-id>--concept--<view>--v001.png`，view 使用 `front`、`side-left`、`side-right`、`back`、`three-quarter` 或 `sheet`。一次修改递增版本；选中图的完整路径记在汇总中，不用覆盖旧图来表示选择。
- 工程名：`<asset-id>.bbmodel`；纹理名：`<asset-id>--<material-or-part>.png`；检查截图名：`<asset-id>--check--<view>--v001.png`。检查点放在 `checkpoints`，如 `<asset-id>--v002.bbmodel`。
- 导出放在 `exports/<target-id>/`，如 `java-geckolib`、`bedrock`；游戏资源名称和扩展名优先服从运行时契约，不强制把源资产命名规则套到已有模组。

新项目示例（只创建本次实际需要的文件夹）：

```text
<project-id>/
  project/
    project-summary.md
    asset-catalog.md
    asset-links.md
    asset-status.md
  concepts/
    <category-id>/<series-id>/<asset-id>/
      <asset-id>--concept--sheet--v001.png
  models/
    <category-id>/<series-id>/<asset-id>/
      <asset-id>.bbmodel
      textures/
      animations/
      exports/<target-id>/
      checks/
      checkpoints/
```

没有系列时省略 `<series-id>`，例如 `models/furniture/oak-chair/`；共享配件可放 `models/attachments/gauss/red-dot-sight/`。按用途分别保存概念图与源模型，由模型 ID 关联；不要在每把枪目录复制一套共享配件源文件。

`project-summary.md` 保存主题、平台、风格和选定参考；`asset-catalog.md` 保存模型清单；`asset-links.md` 有联动时保存关系与接口；`asset-status.md` 保存各资产进度、产物路径、验证与恢复入口。简小任务可在汇总中嵌入清单／联动表，不创建空白文档；已有阶段记录路径保持可用。文档内优先使用相对路径，面向用户报告可用绝对路径。

## Blockbench 模型分组与骨骼命名

采用小写 `snake_case`，如 `root`、`body`、`bolt`、`magazine`、`door_left`、`drawer_01`；左右按模型自身方向，重复部件编号固定宽度。导出的骨骼标识在需要引用的范围内唯一，不使用仅颜色或“组1”来命名运动件。

挂接节点可用 `mount_optic`、`mount_magazine` 等，独立配件可用 `optic_root`；真正的运动父级按运动结构表建立。现有运行时指定了骨骼名、挂接方式或命名空间时优先服从其契约，不能自动重命名；这些例子是默认约定，不是所有 MCP／游戏格式内建的插槽功能。
