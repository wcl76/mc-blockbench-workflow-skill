# 项目访谈与需求汇总

新项目先读本参考；续做任务读取已有简报，只补问缺失或变化的内容。主题确定后可随时制作单件模型，以下编号用于组织提问，不要求依次回答全部问题才开始制作。

## 提问顺序

先后台检查 MCP，同时从用户消息、工程与项目文件提取已有答案。初始访谈优先明确模组类型、平台与整体主题；主题确定后询问模型清单与联动，并按当前任务补齐美术风格、动作和交付信息，每轮只问 1–3 个相关问题；用户一次给全时直接汇总。接入缺失时可穿插询问安装位置，不要让安装打断需求整理。用户不熟悉技术名词时解释用途，允许“暂未决定”，给出标注为建议的候选。

### 1. 模组类型

先问：“你想做哪类模组？例如科技与自动化、家具与建筑装饰、魔法、武器装备、生物与 NPC、探险与维度、农业与美食、仓储与物流；也可以混合或描述自己的想法。第一批最想做什么？”

类型用于组织资产，不是强制分类：

| 类型 | 常见美术资产 |
| --- | --- |
| 科技与自动化 | 机器、管道、电缆、动力装置 |
| 家具与建筑装饰 | 桌椅、灯具、柜子、装饰方块 |
| 魔法 | 法杖、祭坛、符文装置、召唤物 |
| 武器装备 | 枪械、刀剑、护甲、可换配件 |
| 生物与 NPC | 怪物、动物、人物、可动部件 |
| 探险与维度 | 遗迹构件、宝箱、传送装置、环境生物 |
| 农业与美食 | 作物、厨具、食品、加工设备 |
| 仓储与物流 | 箱柜、运输设备、终端、连接件 |

这些是工作流整理的常见方向，可参考 [CurseForge 模组分类及科技模组示例](https://blog.curseforge.com/top-minecraft-tech-mods/)，并非唯一分类体系。若用户只做性能或界面逻辑，先明确是否真的需要三维资产。

### 2. 平台与交付路线

问：“准备用于 Java 版还是基岩版？目标 MC 版本是什么？是加入已有模组／附加包，还是只做资源包？”已有项目优先读配置获得版本和加载器；没有证据不猜。再按当前资产补问具体接收模组／渲染器及版本、使用场景；据 [运行时约定与资产验收](runtime-asset-validation.md) 选择模板和格式，不把 Java／基岩版与模型格式一一对应。

| 目标 | 需要确认 | 工程与导出方向 |
| --- | --- | --- |
| Java 静态方块／物品 | MC 版本，模组或资源包；模组需确认加载器 | Java Block/Item，按版本导出模型 JSON 与 PNG |
| Java 可动生物／武器／机器 | 加载器、渲染与动画库，现有资源契约 | 按运行时选 GeckoLib 或其他兼容格式；不能仅凭“Java”决定 |
| Java 使用代码模型的实体 | 工具链与代码模型要求 | 可考虑 Modded Entity，核对导出与映射要求 |
| 基岩版实体／装备 | 版本、资源包与行为包、实体或 attachable 等用途 | Bedrock Model；按用途交付几何、纹理与动画等资源 |
| 基岩版自定义方块 | 版本与当前方块组件、几何限制 | 验证方块资源契约后选格式，不照搬实体流程 |
| 两个平台 | 各自版本、运行时与交付要求 | 可共享设计规格，分别验证工程／导出，不能承诺一份文件通用 |
| 尚未决定／仅概念图 | 候选平台及选择依据 | 可以先设计，建模前再确定目标格式 |

格式依据见 [Blockbench 格式能力表](https://blockbench.net/wiki/blockbench/formats/)。Java Block/Item 的贴图动画不等同于骨骼动画；Java 生物、机器或手持物品的骨骼动作需要匹配模组运行时。基岩版在编辑器中能播放动画，也仍需游戏侧绑定与触发。格式、旋转和几何限制按目标 MC 版本及当前文档核实。

### 3. 整体主题

问：“整个模组想表达什么主题或世界观？例如近未来高斯科技、蒸汽工业、温馨乡村、古代符文；有没有希望保留或避开的元素？”

把答案整理成 3–5 个设计关键词，确定时代、材料语言、标志性符号和资产之间的共同特征。混合类型仍需共同主题。武器系列可统一能源核心、导轨、配件接口与阵营标识；家具系列可统一木材、五金和比例。

### 4. 模型清单与联动

主题确定后询问：“这个主题下，你已经想做哪些模型？哪些需要共用或替换部件、相互连接或一起运动？”

读取 [模型清单、联动与命名](asset-catalog-naming.md)，根据主题提供少量候选，也允许用户只做当前模型、自由描述或留待以后补充。候选与已决定资产分开记录；当前模型没有关联时记为无，不确定时记为待定。不要求用户一次想全，也不据此自动制作整套资产。

新增模型沿用主题和风格，更新清单；涉及已有主体或共享配件时，只补问影响本次制作的接口与兼容范围。

### 5. 整体美术风格

问：“希望偏原版融合的像素方块风、精细像素工业风、卡通低多边形，还是其他方向？可以提供参考图；配色和细节量有什么偏好？”

把风格落为可执行规则：轮廓与比例、主／辅／强调色、像素密度、材质用贴图还是几何表达、旧化程度、复杂度预算，以及是否允许发光／透明。未知时提出 2–3 个候选并解释差异，不替用户把推荐写成已确认。真实 PBR 或渲染效果必须核对游戏运行时；概念图里的光效不能自动视为游戏支持。

### 6. 当前资产与动作

只补问影响首个交付的问题：先做哪件资产、尺寸、静态或动画、动作清单、是否需要替换、拼装或连接模块、交付目录、已有参考或是否先生成概念图，以及未来可能独立运动的部件。涉及联动时记录接口位置、骨骼／分组命名与纹理策略，避免更换单件时重做整个资产；动画只补问所需触发、播放关系与效果，不要求每件资产都有动作。

## 汇总模板

给用户展示以下“项目设计简报”，按 [模型清单、联动与命名](asset-catalog-naming.md) 保存至项目汇总并维护清单／联动及阶段进度；已有项目保持原记录路径。尚无交付目录时先在对话展示，后续获得目录再保存。每个字段标为“已确认／建议／待定”，不要把建议伪装为用户决定。

| 字段 | 内容及状态 |
| --- | --- |
| 模组类型与当前资产 | 主类型、混合类型、本次制作对象 |
| 模型清单 | 模型 ID、展示名、分类／系列、计划状态与本次范围；允许后续补充 |
| 模型间联动 | 替换、连接、组合运动、共享部件及接口；无／待定／已确认 |
| 目标平台 | Java／基岩版／双平台，MC 版本，模组／附加包／资源包 |
| 技术路线 | 加载器、实际接收模组／渲染／动画库及版本、工程模板、导出格式与资源契约 |
| 使用与验收场景 | 玩家／世界尺度、适用视角、放置／连接／穿戴方式；按用途选择检查 |
| 整体主题 | 世界观、3–5 个关键词、共同设计元素、避开项 |
| 美术风格 | 轮廓比例、配色、像素密度、材质与细节量、参考图 |
| 概念图与材质依据 | 采用参考的路径与版本、材质分区、配色及关键图案、未决差异 |
| 结构与动作 | 尺寸、独立部件、骨骼父级／轴心／运动方向、动作触发／切换／叠加、活动间隙、可替换模块与接口 |
| MCP 接入 | 实现与版本、已连接／待安装／待配置／待重连、实际能力 |
| 安装信息 | 桌面版／网页版、安装位置、AI 客户端；仅在接入需要时记录 |
| 交付与验收 | 目录、可编辑工程、纹理／动画／导出、首个检查点与验证范围 |
| 待定与下一步 | 未决问题、依赖、下一步具体行动 |

汇总随制作和后续需求持续更新，不是开始建模前必须填完的表。汇总后简短邀请用户纠正；已明确授权的下一步继续执行，不重复要求全面确认。只在会改变平台、格式或主要风格的缺失答案上等待；不确定平台时可先做平台无关的设计。后续改动同步简报，系列资产沿用同一主题和风格规则。
